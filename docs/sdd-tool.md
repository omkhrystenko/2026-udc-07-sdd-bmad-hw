# SDD-інструмент (Task B)

**Інструмент:** OpenSpec `1.12.0` (`@fission-ai/openspec`), схема `spec-driven`
**Хост:** Claude Code (Opus 5), Windows 11
**Чому саме він:** репозиторій — TypeScript на Node, а OpenSpec — Node CLI без
додаткових рантаймів. Spec Kit і BMAD обидва тягнуть `uv` + Python; для перевірки
самої ідеї «що інструмент додає понад markdown-спеку» це зайва змінна.

## Встановлення й ініціалізація

```bash
# README курсу радить @latest; фіксую точну версію, щоб цей звіт відтворювався
npm install -g @fission-ai/openspec@1.12.0
openspec init --tools claude --no-animation
```

`init` створив дві речі:

- `openspec/` — `config.yaml` (схема, місце для project context і правил),
  порожні `specs/` і `changes/archive/`. **Закомічено.**
- `.claude/` — 6 скілів (`openspec-propose`, `openspec-apply-change`,
  `openspec-sync-specs`, `openspec-archive-change`, `openspec-explore`,
  `openspec-update-change`) і 6 slash-команд (`/opsx:propose`, `/opsx:apply`,
  `/opsx:sync`, …). **Не закомічено:** `.claude/*` у `.gitignore` цього
  starter-репо. Відтворюється одним `openspec init --tools claude`.

## Що згенеровано

```bash
openspec new change "add-order-discount-engine"
openspec status --change add-order-discount-engine --json   # порядок артефактів
openspec instructions <artifact> --change ... --json         # інструкція + шаблон
openspec validate add-order-discount-engine --strict
```

`openspec/changes/add-order-discount-engine/`:

| Артефакт | Що в ньому |
|---|---|
| `proposal.md` | навіщо зміна, що саме змінюється, які **capability** зачіпає, вплив на код і на споживачів |
| `specs/order-discounts/spec.md` | delta-спека: 9 вимог у формі SHALL/MUST, 16 сценаріїв `#### Scenario:` у форматі WHEN/THEN, з ID `AC-1 … AC-15` у назвах (AC-7 має два сценарії — поріг досягнуто й не досягнуто) |
| `design.md` | 7 технічних рішень (D1–D7) з розглянутими альтернативами, розділ Risks / Trade-offs, план міграції |
| `tasks.md` | 15 задач у 5 групах, кожна з умовою перевірки |

Скелет робить CLI, зміст пишу я. Каркас жорсткий: `openspec status --json`
рахує залежності між артефактами (`specs` заблоковано, поки немає `proposal`),
а `openspec instructions` для кожного віддає окремі `instruction`, `template`,
`rules` і `resolvedOutputPath`.

## Що OpenSpec дав понад звичайну markdown-спеку

**1. Валідатор, який не приймає красиву прозу.** `openspec validate --strict`
перевіряє структуру: кожна вимога має щонайменше один сценарій, сценарій —
рівно чотири решітки (`####`; три «падають тихо», це прямо сказано в
інструкції), нова capability — розділ `## Purpose` довший за 50 символів, а
зміна без жодної дельти відхиляється, якщо не виставлено `skip_specs: true`.
Мою markdown-спеку не перевіряє ніхто, крім рев'ювера.

**2. Розділення «чому / що / як» на три файли, які не можна змішати.**
Інструкція до `specs` прямо забороняє в спеці імена функцій, вибір бібліотек і
покрокові плани («якщо реалізацію можна змінити, не змінюючи зовнішньої
поведінки, — цьому не місце в спеці»). Це змусило винести з моєї спеки речі, які
я туди поклав за звичкою: формула `Math.floor((2n + d) / (2d))` переїхала в
`design.md` як рішення D2, а в спеці лишилось «половина копійки округлюється
вгору». Розділ моєї спеки «Алгоритм (нормативний)» після цього чесніше читати як
design, а не як контракт поведінки.

**3. Примус на альтернативи.** Шаблон `design.md` вимагає для кожного рішення
«why X over Y» і **розглянуті альтернативи**. У моїй таблиці рішень колонка «чому»
була, а «що ще розглядали і чому відкинули» — ні. Саме на цьому кроці з'явилось
D3: коли довелось виписати альтернативу «база категорійного промокоду = початкова
сума категорії», стало видно, що вона ламає каскад D-1 (рівень + категорійний
промокод разом можуть перевищити вартість самих цих товарів). Це не косметика —
це зміна очікуваних чисел в AC-10.

**4. Формат сценарію як заготовка тесту.** `WHEN … THEN` з обов'язковими
конкретними значеннями лягає в тест майже дослівно; ID `AC-N` у назві сценарію
йде далі в `discounts.test.ts` і в `docs/traceability.md` без перекладу.

**5. Граф залежностей замість дисципліни.** `status --json` не дає написати
`tasks.md` раніше за `specs`, а `instructions` для кожного артефакта підтягує
вже готові залежності як контекст. Дрібниця, але саме її люди й порушують.

## Що довелося робити руками

- **Увесь зміст.** OpenSpec не думає: він дає шаблон, інструкцію й валідатор
  структури. Жодного рішення щодо неоднозначностей із тікета він не запропонував
  і жодного не перевірив на суперечливість. «Чому саме так» у таблиці рішень —
  повністю ручна робота, і саме вона займає час.
- **Перенесення ID.** Прив'язку `AC-N` між `docs/spec/pricing-discounts.md`,
  сценаріями OpenSpec, тестами й `traceability.md` тримаю я. Інструмент не
  перевіряє, що сценарій `AC-10` описує те саме, що критерій `AC-10` у спеці.
- **Зворотна перевірка** (код без AC, AC без тесту) — теж руками; OpenSpec
  зупиняється на плануванні й у код не заглядає.
- **Дублювання.** Тепер поведінка описана двічі: в `docs/spec/pricing-discounts.md`
  (українською, з розділом «чому») і в `openspec/changes/.../spec.md`
  (англійською, у форматі інструмента). Це реальна ціна: два документи треба
  тримати синхронними, і при наступній правці розійтись вони можуть мовчки.
  Якби це був не навчальний репозиторій із заданими шляхами, я б лишив один —
  спеку OpenSpec, а «чому» переніс би в `design.md`, де для нього і є місце.
- **Мова.** Артефакти OpenSpec написані англійською, бо англійські й шаблони, і
  формат `SHALL`/`WHEN`/`THEN`. Людські документи курсу лишились українською.

## Чесний підсумок

На фічі такого розміру OpenSpec **не змінив жодного мого рішення сам** — але
змінив одне (D3/AC-10) тим, що вимагав виписати альтернативи, і одне (межу між
специфікацією та дизайном) тим, що має валідатор із думкою. Тобто цінність тут
не в генерації, а в **обов'язковій структурі**: інструмент не дає зупинитись на
рівні «ну, це й так зрозуміло».

Далі: `/opsx:apply` виконує `tasks.md`, `openspec archive` зливає дельту в
`openspec/specs/order-discounts/spec.md` як основну спеку. Реалізацію (Task C) я
робив за `tasks.md` руками, а зміну не архівував — щоб у PR було видно і дельту,
і сам change-каталог.
